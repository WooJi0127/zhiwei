# 2026-10-16

## K-Pop 回归追踪器（从零开发，v1 完成）

用户需求：重度 K-pop 听众，想追踪未来一个月回归 + 留存历史发行，需搜索/筛选/收藏/本命置顶，不需播放（跳转外部平台），每天定时更新。

### 调研结论
- GitHub 开源项目无一可用：kpop-tracker 只追 Spotify 播放量；concert-tracker 类只做演唱会。**从头开发**。
- 数据源实测（关键，都验证过）：
  - **kpopping.com** —— 日历页内嵌 RSC JSON（`initialEvents` 按日期分组，含 releases/concerts/anniversaries）。
    提取方法：把 `\"` 还原成 `"` 后，用正则锚定 `"YYYY-MM-DD":{`，再对 `"releases":[` 做括号平衡切片 + json.loads。
    注意：整块 JSON 直接 parse 会因转义残留失败，必须分段提取。**这是唯一能拿到未来发行的源**。
  - **Apple Music iTunes API** —— `search?entity=musicArtist` 拿 artistId（同名艺人取 K-Pop genre 且作品最多者），
    再 `lookup?id=&entity=album` 拉专辑。**实测拿不到未来发行**（预购专辑不进 API），只能做历史归档。
    提供 collectionViewUrl 深链、artworkUrl100 封面（可替换成 600x600）。
  - **kpopcal.com/api/events.json** —— CC BY 4.0，52 艺人/225 事件，带 source 溯源。覆盖稀疏，作补充。
  - Deezer / MusicBrainz 本次不通；QQ音乐无公开 API（只能构造搜索链接）。

### 架构决策（用户已确认）
- 形态：**本地单机版**。单 HTML 双击打开 + Python 脚本 + SQLite。
- 关键坑：file:// 下 fetch 本地 JSON 会被 CORS 拦。解法是导出 `data.js`（`window.__KPOP_DATA__=...`）用 `<script src>` 加载。
- 脚本**纯标准库**（urllib+sqlite3+json），零 pip 依赖，避免用户环境装包失败。
- 追踪范围：韩语专辑/单曲 + 新团出道；排除 OST/Remix/Instrumental/日文中英版本。
- 跳转：只 Apple Music（精确深链，无则回退搜索链接）。
- 更新：Windows 计划任务，每天 08:00。

### 产出
- `KpopTracker.html` 主程序（4 个 tab：即将回归/历史归档/收藏/本命；筛选+搜索+localStorage 收藏与本命）
- `scripts/sources.py`（三源抓取，带重试退避）、`scripts/build.py`（入库+导出，原子替换，单源失败不影响整体）
- `update.bat`（手动）、`install_task.bat`（注册计划任务）
- 首跑全量结果：217 艺人 / 1439 发行 / 225 事件 / data.js 705KB

### 遗留 / 提醒
- **schtasks 被沙箱安全策略黑名单拦截**，无法代用户注册计划任务 → 必须让用户自己双击 `install_task.bat`。
- Apple Music 有 7 天缓存（AM_CACHE_DAYS），所以每日增量很快；`--full` 全量约 24 分钟。
- anniversaries 的 isDebut 未抓到值，出道年主要靠 kpopcal，覆盖率有限 → 新团识别可能漏。后续可补 kpopping 团体页。
- 若要做成大众可用的网站：data.js 换后端 API + 托管 DB，SQLite 历史可直接迁移。

### 数据层增强
- **曲目数据**：iTunes `lookup?id={artistId}&entity=song&limit=200` 一次拿该艺人全部曲目，
  再按 collectionId 归组到专辑。**关键坑：按 collectionId 查 entity=song 返回 0，必须用 artistId。**
  结果：1144 张专辑 / 3593 首曲目
- **韩文归一**：kpopping 日历与 Apple Music 韩国区都会返回韩文艺人名。
  解法：用韩文名反查 Apple Music `search?entity=musicArtist`，取返回的英文 artistName。
  111 个韩文名 → 归一 89 个，剩余为罕见合作曲。
  注意：`itunes_search_artist` 的严格评分对韩文查询无效（返回英文名与查询词不像），
  必须用宽松版 `itunes_search_artist_any`（优先取 K-Pop 分类结果）。
- **合作曲归主艺人**：`names.reconcile_artist` 把 'Alok, 나연 & TWICE' 归到 'TWICE'
- **去重**：kpopping 与 Apple Music 会收录同一张专辑，按 (艺人, 归一化标题, 日期) 合并，
  优先保留有曲目的。合并 102 条。
- **中文名表**：`scripts/names.py` 的 ARTIST_ZH_OFFICIAL，只收可靠中文名（41 条），
  不做直译（Stray Kids 不译成"流浪儿童"）。

### 踩过的坑（重要，下次别再踩）
1. **中文文件名 + headless Edge 会卡死**：`file:///.../知未.html` 在 `--dump-dom` 下超时（exit 124）。
   测试时先复制成 ASCII 文件名的副本（如 `tmp_test.html`）再渲染。用户双击打开不受影响。
2. **Python subprocess 调 Edge 会超时**，改用 bash 直接调 + `--user-data-dir` 独立 profile 才稳定。
3. **局部变量名覆盖模块名**：`step_apple_music` 里的 `names = [...]` 覆盖了 `import names`，
   报 `'list' object has no attribute 'norm_artist'`。已改名 `artist_names`。
4. **iTunes ON CONFLICT 要显式更新 artist 字段**，否则旧的韩文/组合艺人名永远刷不掉。
5. **大小写不同会被当成两个艺人**（YOUHA / Youha），导出时用 `known_lower` 归一。
6. 反查韩文名必须用宽松搜索 `itunes_search_artist_any`：严格评分逻辑是拿返回的
   artistName 跟查询词比对，而用韩文搜返回的是英文名，永远打不到阈值。

## v2.1 迭代（10/17 凌晨，用户反馈 4 个问题）

### 修的 bug
- **时间筛选改不了**：`renderList` 里 upcoming tab 先做了 `ALL.filter(r=>_dd>=0)` 预过滤，
  导致日历选到过去的区间直接空白。**移除预过滤**，改为分组渲染并加「更早 / 已发布」组；
  history tab 同理不再只显示过去。已用 URL hash 参数验证：选 2026-08-01~09-30 出 210 张卡片。
- **tab 按钮高亮不同步**：初始化时没调 `syncTabs()`，URL 直接指定 tab 时按钮不亮。
- **卡片显示的是经纪公司全称**：前端取了 `a.agency`，应取 `a.parent`（母公司）。

### 数据准确性提升
- **艺人类型（group/solo）覆盖 52 → 83%**：
  ① kpopcal 只给 52 个艺人，太稀疏
  ② 新增 `sources.fetch_kpopping_roster()`：抓 /groups(281团体) 与 /idols(438个人) 列表页
  ③ 日历页的 birthdays.name → solo；anniversaries.group → group（改 `fetch_kpopping_month`
     返回 4 元组）
  ④ `names.py` 的 KNOWN_GROUPS / KNOWN_SOLO 手工名录兜底（`step_kind_fallback`）
- **经纪公司归母公司**：`names.AGENCY_PARENT` + `parent_agency()`，
  先去掉 `(...)` 再精确匹配、最后模糊匹配。结果从一堆子公司收敛到 **14 个母公司**。
- **发行类型精准化**：`catOf()` 按原始 rtype 分 5 类（正规专/迷你专/单曲/后续专/合辑），
  `typeLabel()` 显示中文。分布：单曲 876 / 迷你专 264 / 专辑 187 / 合辑 1。

### 数据源再探测（用户要求「用各种方式找」）
又测了 4 个源，结论是**都不值得接入**：
- Deezer、Wikipedia：网络不通（502 Tunnel）
- Discogs：能通，有 credits 字段，但 K-pop 专辑 credits **全部为 0**，
  且按「艺人+专辑名」搜索会错配（IVE REVIVE → 牙买加雷鬼专辑）。
  全量接入需 2656 次请求 ≈ 2 小时，收益为零。
- MusicBrainz：老牌艺人有（TWICE 955 条），新专辑 0/6。

### 结论（重要）
「制作团队」这条路**目前堵死**，除非接受「爬 Melon + 反爬对抗 + ID 映射」的不稳定方案。
风格粒度也只能停在 `K-Pop` 一级。已如实告知用户，没有编造数据。
